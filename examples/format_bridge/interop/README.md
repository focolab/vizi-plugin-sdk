# Interop — crates written by each implementation

Not fixtures. [`../fixtures/`](../fixtures/) is pinned and generated by a
committed recipe; this directory holds crates that an *implementation's own
writer* produced, so that every implementation can open a file it did not
make. Opening one is the interop test [`../SPEC.md`](../SPEC.md) describes.

Each file is `<language>.crate`, written by that implementation's host-free
`recreate` command from `../fixtures/sample.crate`; the command is in each
implementation's README. `scala.crate` is a crate written by another implementation
from the same input, kept as test data.

## `python.crate`

2162 bytes, SHA-256
`795a3840fd9be488eddd2a289112acded2230dceee597d31a43c22c4129f3905`.

Written by the Python implementation:

```bash
cd ../python && .venv/bin/python crate_tool.py recreate ../fixtures/sample.crate ../interop/python.crate
```

It is semantically equal to `sample.crate` — same `3×2×4×6×5` u16 volumes,
the same 443-byte `ome-xml` document, the same `(2.0, 0.325, 0.325)` µm and
1.5 s calibration — and **not** byte-equal: its blocks are laid out in
**ascending** canonical order (offsets `546, 786, 1026, 1266, 1506, 1746`)
where the fixture's are in reverse. A reader that opens one and not the other
is computing offsets instead of reading the index.

## The others

`go.crate`, `rust.crate`, `java.crate` and `scala.crate` are the same 2162
bytes, with the same SHA-256: the format section of `SPEC.md` pins a file
byte for byte, and every writer produces it.
